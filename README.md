# Remote Control Hub

A lightweight remote control and operations platform for managing connected Python-based clients through a web UI.

It combines an interactive shell, remote file operations, script execution, background jobs, artifact collection, agent building, and session-based web access control in a single project.

> **Important**
> Use this project only in environments you own or are explicitly authorized to manage. The repository includes powerful remote execution and persistence-related utilities and should be treated as an administrative/automation tool for controlled use.

## Overview

Remote Control Hub is a server/client project for operating remote endpoints from a browser-based control panel.

At a high level, it provides:

- A **web console** for shell-like command execution and live output streaming
- A **device list** with online/offline status
- A **remote file browser** with common file operations
- **Artifacts** for previews and downloads
- **Scripts** for one-shot actions organized by directory
- **Background jobs** for long-running or repeated monitoring tasks
- **Process/app inspection** and kill operations
- **Command history** and execution history views
- **Agent builders** for multiple delivery modes
- A simple **session-based auth layer** plus static API token support

The current implementation is intentionally lightweight and file-based. It does not require a database and stores runtime state under `runtime/`.

## Core Capabilities

### 1. Device management

- Lists active client sessions in the left sidebar
- Displays connection metadata such as hostname, IP, platform, integrity, RTT, working directory, and client ID
- Supports recent-device caching so previously seen hosts remain visible as offline entries after refresh
- Uses hostname-based merging for the recent-device cache

### 2. Interactive command execution

- Sends commands from the web UI to the selected client
- Streams command output back to the UI
- Supports command candidates / autocomplete sourced from both server-side built-ins and client manifests
- Includes task cancellation for active web-submitted commands

### 3. Remote file browser

- Browse remote directories
- Create folders
- Rename files/folders
- Delete single or multiple entries
- Download files
- Download multiple paths as a zip archive
- Copy / cut / paste remote paths
- Preview and save remote file content
- Support hidden-file visibility toggle
- Manage pinned quick-jump paths

### 4. Artifact center

- Collects files uploaded from clients or generated by jobs/commands
- Browse artifacts by type and hostname
- Download raw files
- Preview supported artifact content
- Edit artifact content server-side
- Clear artifacts by category

### 5. Process and app inspection

- Enumerate running processes
- View process detail
- Kill processes
- Enumerate running apps separately from raw process views
- Kill apps from the UI

### 6. Script library

- Organizes scripts by directory under `server/resources/scripts/`
- Provides a Script Library dialog with folder navigation and per-script actions
- Supports script metadata via `SCRIPT_METADATA`
- Supports structured script execution via `run_script` while keeping legacy command-style execution paths intact
- Supports script editing, upload, creation, and deletion from the UI

### 7. Background jobs

- Lists server-managed job modules from `server/resources/jobs/`
- Supports metadata-driven job catalog presentation
- Supports parameterized job start requests
- Supports job start/stop lifecycle from the web UI
- Supports job result reporting back to the server

### 8. Agent generation

- Build downloadable client artifacts from the web panel
- Includes multiple build modes such as:
  - **PyInstaller**
  - **Bundle**
  - **Go (Simple)**
  - **Go (Loader)**
- Injects build/version metadata into generated outputs
- Exposes build and download APIs

### 9. Authentication and access control

- Session-based web login with a fixed admin username/password
- Static token support for API access from tools such as Postman or `requests`
- Route-level anonymous access support via annotation/guard pattern in selected endpoints

## Architecture

The project is split into four main parts:

### `server/`
The central web/API and control orchestration layer.

Responsibilities include:
- session and connection registry
- command dispatch
- artifact persistence
- history persistence
- remote file operations orchestration
- script/job catalog and execution requests
- agent build pipeline
- recent-device cache
- web auth

### `client/`
The Python client runtime that connects back to the server and executes commands/jobs/scripts.

Responsibilities include:
- transport and session initialization
- command execution
- background job execution
- upload and HTTP transfer helpers
- platform-specific command support
- watchdog behavior

### `core/`
Shared protocol and utility code used by both server and client.

Responsibilities include:
- protocol helpers
- logging utilities
- shared helpers

### `static/`
The browser UI.

Responsibilities include:
- connection list UI
- interactive shell
- file browser
- artifact preview/editing
- history dialogs
- process dialogs
- script/job management dialogs
- login page and auth bootstrap

## Jobs and Scripts

### Background jobs

Background jobs are long-running tasks managed by the server/client job framework.

Current job system highlights:
- job catalog APIs
- metadata-driven parameter forms
- start / stop controls
- report ingestion
- support for platform tags and parameter schemas

Typical use cases:
- monitoring application launches
- clipboard monitoring
- screenshot or scheduled capture flows

### Scripts

Scripts are one-shot utilities stored under `server/resources/scripts/`.

Current script system highlights:
- directory-based organization
- metadata via `SCRIPT_METADATA`
- script library UI with folder navigation
- edit/upload/delete support
- structured execution via `/api/connections/<client_id>/scripts/run`

This makes scripts well-suited for:
- small data collection tasks
- platform-specific admin actions
- quick UI prompts or persistence helpers
- repeatable one-off actions that do not need a full job lifecycle

## Agent Build Modes

The project exposes agent-building features from the web UI.

### PyInstaller

- Builds a Python client executable for the current server platform
- Injects build metadata
- Good for environments where Python source bundling is not desired

### Bundle

- Packages `client/`, `core/`, and `ratclient.py` into a zip archive
- Injects build version into the bundle configuration
- Designed for source-based delivery/update flows

### Go (Simple)

- Intended as the simplified Go client builder path
- Keeps cross-platform build-style options exposed in the UI

### Go (Loader)

The Go loader has a different responsibility from the simple Go build.

Current loader responsibilities include:
- collecting local environment basics such as OS/arch/host/IPs
- reporting to the server via HTTP
- detecting Python availability and reporting the result
- resolving a working directory under the user home directory
- requesting a fresh bundle build from the server
- downloading and extracting the bundle
- launching `ratclient.py` via `python3` / `python`
- reporting launch details (paths, PID, build version)
- exiting after handoff

The server side includes a loader report endpoint that currently writes JSON-line style logs under runtime logs.

## Authentication

The web app includes a lightweight auth layer designed for simple public deployment scenarios.

### Supported auth methods

- **Session login** for the browser UI
- **Static API token** for external API clients

### Current characteristics

- fixed admin username/password stored in server config / environment variables
- no registration flow
- no database dependency
- session cookie based login for the web app
- API token accepted via auth guard

### Relevant config entries

- `RAT_WEB_SESSION_SECRET`
- `RAT_ADMIN_USERNAME`
- `RAT_ADMIN_PASSWORD`
- `RAT_ADMIN_API_TOKEN`
- `RAT_WEB_AUTH_SESSION_DAYS`
- `RAT_WEB_SESSION_COOKIE_NAME`

## Runtime Data

The project stores runtime data under `runtime/` rather than a database.

Examples include:

- artifacts
- command history
- pinned paths
- web files / previews
- agent build outputs
- loader logs
- recent devices cache

### Recent devices cache

A lightweight recent-device cache is maintained at:

```text
runtime/recent_devices.json
```

Current behavior:
- one record per hostname
- online device updates overwrite prior cached state
- offline devices remain visible as recent entries after refresh

## Development Notes

### Front end

The current UI is a classic static app structure with modular JavaScript and Element Plus style components. It is not yet on a Vite + Vue 3 full build pipeline.

### Metadata-driven extensibility

The project now uses metadata-style declarations in both jobs and scripts:

- `JOB_METADATA`
- `SCRIPT_METADATA`

This enables:
- platform filtering
- parameter prompting
- richer catalog views in the UI

### Storage model

The current architecture intentionally favors:
- runtime JSON/files
- lightweight stores
- no database setup

That keeps iteration fast, but some subsystems still need convergence and cleanup.
